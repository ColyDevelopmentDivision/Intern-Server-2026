# 追加課題D: コストを消費する

**目的**: ガチャを引く時に、魔石を実際に減らします。これで「引けば引くほど魔石が減る」ゲームらしい挙動になります。

**目安時間**: 10〜15分

**この課題のゴール**: Alice (魔石3000) が通常ガチャを1回叩くと魔石が **0** になり、2回目は BadRequest で拒否される状態です。

**前提**: [メイン課題1](../1-draw.md) + [追加課題A](./A-user-id.md)/[B](./B-grant.md)/[C](./C-check.md) 完了済み

---

## ミッション

**ガチャを引いたら魔石が実際に減るようにしよう**。Alice (魔石 3000) が通常ガチャを 1 回叩くと魔石が 0 になり、2 回目は BadRequest で拒否される状態にする。

### 1. 所持数を減らす処理を実装

`src/InternApi/Services/UserItemService.cs` の `ConsumeAsync` を実装しよう。指定アイテムを consumeCount 個減らす処理を書く。

### 2. Draw の中でコスト消費を挟む

`GachaDrawController.Draw` で、**コスト所持チェックの直後・抽選の直前** に (1) で作った処理を呼び出す。

> 💡 順序が重要です: 所持チェック → 消費 → 抽選 → 付与 の順。この順序が崩れると整合性が破綻します。[統合演習 (追加課題E)](./E-integration.md) でこの順序の重要性を掘り下げます。

## 動作確認

Swagger で `POST /api/gacha/draw` を叩いた前後で、そのユーザーの魔石の数がどう変わるか観察しよう:

```json
{ "gachaId": 1, "userId": 1 }
```

- 引く前と引いた後で魔石の数はどう変わるか
- 同じ Draw を続けて叩いていくと、どこかで挙動が変わる瞬間があるはず。何回目で、どう変わるか観察してみよう
- **もし変な状態に落ちたら**（魔石がマイナスになる、無限に引けてしまう等）、消費のロジックを見直そう

使えるツール:
- `GET /api/debug/inventory?userId=1` — 所持一覧を確認
- `POST /api/debug/item-consume?userId=1&itemId=1001&consumeCount=300` — `ConsumeAsync` を単体で試したい時
- `POST /api/debug/item-give?userId=1&itemId=1001&grantCount=3000` — 魔石を補充してリトライしたい時

> ツールの起動・操作方法は [動作確認マニュアル](../../動作確認マニュアル.md) を参照
