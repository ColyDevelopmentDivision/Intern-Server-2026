# 追加課題A: userId を受け取って「本当に新しい」を判定する

**目的**: `POST /api/gacha/draw` のリクエストに `userId` を追加して、そのユーザーが「今回初めて手に入れたアイテムだけ isNew=true」にします。

**目安時間**: 15〜20分

**前提**: [メイン課題1](../1-draw.md) + [メイン課題2 (マスタいじりワーク)](../2-master-workshop.md) 完了済み (`POST /api/gacha/draw` で 10連の抽選結果が返り、マスタ操作でゲーム挙動が変わることを体感済みの状態)

> 💡 メイン課題2 でマスタを書き換えたままだと、A の動作確認 (Alice の所持アイテム 2005 が isNew=false になる、など) が読みにくくなります。動作確認前に、[メイン課題2 の「リセット方法」](../2-master-workshop.md#リセット方法) に従って初期状態に戻しておくと安全です。

---

## ゴールと現状

### ゴール

そのユーザーがすでに持っているアイテムの場合は `isNew=false` にする。

→誰が引いているかを Server が意識し始め、ガチャ検証ツールから「ユーザーごとの体験」への第一歩となります。

### 現状

`isNew` は「その10連の中で初めて出たアイテムだけ true」という単純な判定です。

```json
{ "gachaId": 1 }
```

で `POST /api/gacha/draw` を叩くと、結果に `isNew` が返ってきますが、これは **同じ10連の中の重複チェック** です。

Alice (userId=1) は初期状態で `森の弓使い (item_id=2005)` を1個持っています。

> 💡 phpMyAdmin ([http://localhost:8080](http://localhost:8080)) → `intern_user` → `user_items` テーブルで `user_id=1` の行を確認できます。

---

## ミッション

**リクエストで `userId` を受け取れるように改修**して、そのユーザーが「本当に初めて手に入れた」アイテムだけ `isNew=true` になるようにしよう。

### 1. サーバー側

`POST /api/gacha/draw` の**リクエスト（InParam クラス）** に `userId` を受け取れるように追加し、`isNew` の判定を **「そのユーザーが既に持っているアイテムかどうか」** で判断する形に書き換える。

### 2. Unity から API を叩く場合

この課題では **`userId=1` を送る想定** なので、クライアントワーク側のソースコードでも `1` を送るように書き換えてください。

詳しくはスタッフに確認してください。

## 動作確認

サーバー再起動後、Swagger で以下を試します:

**Alice (userId=1) は初期状態で `2005 (森の弓使い)` を1個持っています**:

```json
{ "gachaId": 1, "userId": 1 }
```

- 結果に `2005` が含まれる場合、**isNew は false** になります (Alice は既に持っている)
- 結果に `2001 (炎の勇者)` などが含まれる場合、**isNew は true** になります (Alice は持っていない)

**Charlie (userId=3) は魔石以外の排出品を持っていません**:

```json
{ "gachaId": 1, "userId": 3 }
```

- ほぼ全ての排出結果で **isNew=true** になります (Charlie は排出品を持っていないので全部初出)
- **10連の中で同じアイテムが2回以上出た場合、`isNew` の付き方は実装によって変わります**。Swagger で自分の実装がどうなっているか確認してみてください
- **ユーザー目線で考えてみよう**: 「両方 isNew=true にして新規獲得の演出が2連発」と「1回目だけ isNew=true にして初獲得の演出は1回だけ」、どちらがわかりやすい表示でしょうか？
- わかりやすいと思った方の挙動になるように、自分の実装を調整してみましょう（[統合演習 (追加課題E)](./E-integration.md) でも「10連内重複をどう扱うか」を検討します）

> ツールの起動・操作方法は [動作確認マニュアル](../../動作確認マニュアル.md) を参照

## この課題の学びどころ

- **API 仕様変更**: InParam はサーバー側と Unity 側（送信元）で揃える必要があります。片方だけ変わっていると通信が成立しないので、クライアントとサーバーで協力して進めることになります。
- **処理を分けておく恩恵**: 「所持アイテムを取得する処理」が既に `Services/` の中に用意されているので、呼び出すだけで isNew の判定ができます。処理を役割ごとに分けておくと、追加のコードが最小限で済みます。
- **同じ isNew でも解釈が変わる**: 実装によって「何を『新しい』とするか」が変わります。細かい挙動は仕様に明記されないことが多いので、**エンジニアからプランナーへ「こういう挙動でどうか？」と提案しながら、一緒により良い仕様を作っていく**ことになります。
