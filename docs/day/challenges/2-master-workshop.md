# メイン課題2: マスタいじりワーク — DB を直接触ってゲーム挙動を変えてみよう

**目的**: phpMyAdmin から `intern_master.gacha_detail_master` の `weight` を直接書き換えて、`POST /api/gacha/draw` の結果が変わることを体感します。**コード一行も書かずに** ゲームバランスが変えられる、マスタ駆動設計の醍醐味を掴む課題です。

**目安時間**: 5〜10分

**この課題のゴール**: 通常ガチャ (gacha_id=1) の SSR の `weight` を書き換えて、10連で SSR が半分くらい出るガチャに変えられること。

**前提**: [メイン課題1](./1-draw.md) 完了済み (`POST /api/gacha/draw` で 10連の抽選結果が返る状態) / phpMyAdmin ([http://localhost:8080](http://localhost:8080)) からマスタ DB (`intern_master`) が見える

---

## なぜマスタを直接触るワークをやるの？

ゲーム開発では **「マスタが動作を決める」** という設計思想が広く使われます:
- 排出確率、ダメージ計算、キャラクターの能力値、イベント報酬、ショップ商品ラインナップ...
- これらは基本的に **DBのマスタテーブル** に載っていて、企画 (プランナー) が調整します
- 実装エンジニアは「マスタを読み取って処理する仕組み」を作るのが仕事

つまり、**同じコードでもマスタが違えばゲーム体験は全く変わります**。メイン課題1 で書いた抽選ロジックが「マスタから取ってくる」形になっているので、マスタ側の値を触るだけで挙動が変わることをここで確認します。

---

## ミッション

通常ガチャ (gacha_id=1) の排出確率を書き換えて、SSR が半分の確率で出るガチャにしよう。

1. phpMyAdmin にアクセス → 左ペインで `intern_master` を選択
2. `gacha_detail_master` テーブルをクリック → 「表示」タブ
3. `gacha_id=1` の `item_id=2001` (炎の勇者、SSR) の行を探す
4. 「編集」ボタン → `weight` を `1` から **`50`** に変更 → 「実行」
5. 同じく `item_id=2002` (氷の魔導士、SSR) も `1` → **`50`** に変更

> 💡 phpMyAdmin の操作方法は [動作確認マニュアル](../動作確認マニュアル.md) を参照。

---

## 動作確認

Swagger で `POST /api/gacha/draw` に以下を投げます:

```json
{ "gachaId": 1 }
```

**期待する変化**:
- 修正前: SSR は 100連引いても数回しか出ない
- 修正後: 10連で SSR が **半分くらい (5〜6枚)** 出るようになる
- 他のレアリティは相対的に排出が減る

> 💡 **サーバーの再起動は不要** — マスタを書き換えた直後に Swagger を叩くだけで結果が変わります。サーバー側は毎回 DB からマスタを読み直しているので、コード側は何も触らずに挙動が変わることを実感できるはずです。
>
> （「サーバーの再起動」= `dotnet run` を実行しているターミナルで `Ctrl + C` で止め、`dotnet run --launch-profile http` で再度起動する操作。コード変更時には必要ですが、この課題では **一切実行しなくてOK** です。）

「今の設定を再確認したい」時は phpMyAdmin で `gacha_detail_master` の値を見返してみよう。

## この課題の学びどころ

- **weight は絶対値ではなく相対比率**: 他の weight を触らずに1個だけ大きくすると、そのアイテムが圧倒的に出やすくなり、他のアイテムは相対的に確率が下がります。実務ではこれを「バランス調整」と呼び、プランナーが数字を触るだけで完結する仕組みは大きな価値があります
- **コードを変えずにゲーム挙動を変えられる**: メイン課題1 で「マスタから取ってくる」構造にしておいたおかげで、DBの値を触るだけで排出が変わります。実装が拡張に対して開かれている状態です
- **pma で本番DBを直接触るのは実運用ではNG**: 教材だからこそ許される手段です。監査ログが残らず、SQLのタイポでデータが壊れても履歴が追えません。本番では「マスタ管理画面 (プランナー用Webツール)」や「migrations (Git管理された SQL ファイル)」経由でしか変更しないのが定石。この違いを頭に入れつつ、まずは体感するのが今日の狙い

---

## リセット方法

pma で書き換えたデータを **一括で元の初期状態に戻したい** 時:

```sh
docker compose down -v
docker compose up -d
```

- `-v` はボリューム削除。これで `docker/mysql/init/*.sql` が再実行され、DBが最初の状態に戻ります
- `user_items` (Alice の魔石など) もリセットされるので、ガチャ実行状態も初期化されます
- **追加課題A に進む前にリセットしておくと、A の動作確認 (Alice の所持アイテム判定など) が読みやすくなります**
